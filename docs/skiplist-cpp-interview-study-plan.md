# Skiplist-CPP 存储面试学习与改造方案

## 1. 是否适合作为简历项目

结论：适合，但只能作为“起点项目”，不适合作为“原样直接写进简历的成品项目”。

原因：

1. 这个项目覆盖了存储开发面试里最基础的一条链路：内存数据结构、增删查、简单持久化、并发访问、性能压测。
2. 代码量小，适合你在短时间内完整吃透，面试时不容易被追问到答不上来。
3. 它的短板也很明显：现在更像“跳表算法 Demo”，而不是“真正可讲工程细节的存储引擎”。
4. 如果你能完成一轮工程化改造，它就可以升级成一个很好的校招或初中级社招存储方向项目。

建议你的定位：

1. 不要把它包装成“我实现了 Redis/RocksDB”。
2. 应该把它包装成“我从一个跳表 KV Demo 出发，补齐了并发安全、测试、持久化恢复和性能基准，做成了一个可解释的轻量级 KV 存储引擎”。

一句话判断：

1. 原样写进简历，竞争力一般。
2. 做完本文档里的 P0 + P1 改造，再写进简历，竞争力明显提高。

## 2. 我对当前项目的深入理解

### 2.1 项目目标

这个仓库实现的是一个基于跳表的轻量级 KV 存储引擎，核心功能包括：

1. 插入 `insert_element`
2. 删除 `delete_element`
3. 查询 `search_element`
4. 展示 `display_list`
5. 落盘 `dump_file`
6. 加载 `load_file`
7. 返回元素数量 `size`

当前持久化模型不是 WAL，也不是 LSM-tree，而是最简单的“把当前内存中的全量有序数据写回文本文件”。

### 2.2 核心文件职责

1. `skiplist.h`
   当前几乎全部核心逻辑都在这里，是一个 header-only 的实现。
2. `main.cpp`
   只是演示程序，负责插入几条中文数据、查询、删除、落盘。
3. `stress-test/stress_test.cpp`
   压测程序，目前只做了插入压测，线程数默认是 1。
4. `stress_test_start.sh`
   负责编译并执行压测。
5. `store/dumpFile`
   运行 demo 后生成的文本存储文件，格式是 `key:value`。

### 2.3 数据结构设计

#### Node

`Node<K, V>` 保存：

1. `key`
2. `value`
3. `node_level`
4. `forward`

其中 `forward` 是一个指针数组，长度为 `level + 1`，表示该节点在不同层上的后继指针。

#### SkipList

`SkipList<K, V>` 保存：

1. `_max_level`
2. `_skip_list_level`
3. `_header`
4. `_element_count`
5. `_file_writer`
6. `_file_reader`

这是一个典型的跳表实现：

1. 头节点 `_header` 作为每一层的入口。
2. 每次插入通过自顶向下查找插入位置。
3. 新节点层高通过随机函数生成。
4. 删除时维护一个 `update[]` 数组来回接前驱节点。

### 2.4 核心数据路径

#### 插入流程

`insert_element` 的流程是：

1. 从最高层开始查找待插入位置。
2. 用 `update[]` 记录每一层上待插入节点的前驱。
3. 如果 key 已存在，则直接返回，不更新 value。
4. 随机生成新节点层高。
5. 如果新层高超过当前跳表层高，则补齐高层前驱为 `_header`。
6. 在每一层把新节点插入到前驱和后继之间。

面试时你要能解释：

1. 为什么查找、插入、删除平均复杂度是 `O(log n)`。
2. 为什么 `update[]` 是必须的。
3. 为什么跳表比红黑树更容易做工程化改造和范围扫描。

#### 查询流程

`search_element` 的流程是：

1. 从最高层开始向右查找，直到下一跳 key 不再小于目标 key。
2. 逐层下降。
3. 在第 0 层检查目标节点是否存在。

这是标准跳表查找路径，面试时通常会让你手画一遍。

#### 删除流程

`delete_element` 的流程是：

1. 和插入一样先找到每一层的前驱节点。
2. 如果目标 key 存在，就让各层前驱绕过当前节点。
3. 如果高层已空，递减 `_skip_list_level`。
4. 删除节点，元素数减一。

#### 持久化流程

`dump_file` 的流程是：

1. 顺着第 0 层遍历整张跳表。
2. 按 `key:value` 的文本格式逐行写入 `store/dumpFile`。

`load_file` 的流程是：

1. 逐行读取 `store/dumpFile`。
2. 用 `:` 切分 key 和 value。
3. 对 key 调用 `stoi` 转回 int。
4. 调用 `insert_element` 重建跳表。

### 2.5 本地运行结论

我已经在本地执行过：

1. `make`
2. `./bin/main`
3. `sh stress_test_start.sh`

结论：

1. demo 可以正常运行，插入、查询、删除、落盘链路都能走通。
2. 压测也能跑通，但当前压测输出了大量日志，结果会被 I/O 干扰。
3. 压测默认线程数是 1，因此它并不能证明真正的并发能力。

## 3. 当前项目的关键问题

这一部分很重要，因为它决定了面试官会不会认为你只是“照着教程敲了一遍”。

### 3.1 这是一个算法 Demo，不是完整存储引擎

现状：

1. 只有内存跳表和全量文本落盘。
2. 没有 WAL。
3. 没有崩溃恢复一致性设计。
4. 没有分层存储。
5. 没有后台 compaction。

影响：

1. 更像课程练手项目。
2. 面试官如果问“掉电一致性怎么保证”，当前项目答不圆。

### 3.2 头文件里放了全局变量

`skiplist.h` 里直接定义了：

1. `std::mutex mtx`
2. `std::string delimiter = ":"`

问题：

1. 这是头文件定义，不是声明，多翻译单元场景下会有 ODR 风险。
2. 所有 `SkipList` 实例共享同一把全局锁，不合理。
3. 分隔符也不该是进程级全局可变状态。

### 3.3 线程安全并不完整

现状：

1. `insert_element` 和 `delete_element` 使用全局 `mtx`。
2. `search_element` 没有加锁。
3. `dump_file` 和 `load_file` 也没有做一致性保护。

问题：

1. 读写并发会有数据竞争。
2. 遍历过程中如果其他线程修改链表，可能读到不一致状态。
3. 这个实现不能严格宣称“线程安全”。

### 3.4 模板接口不够泛化

现状：

1. 类型模板参数写成了 `SkipList<K, V>`。
2. 但 `load_file` 里对 key 直接调用 `stoi`。

问题：

1. 这导致代码表面上泛型，实际上 key 基本被写死成 `int`。
2. 一旦面试官问“模板意义是什么”，你需要承认这里是半泛型设计。

### 3.5 工程质量较弱

现状：

1. 没有 include guard 或 `#pragma once`。
2. 没有命名空间。
3. 大量使用裸指针和手工内存管理。
4. 析构依赖递归 `clear`，数据量大时有栈深风险。
5. 函数内部大量 `std::cout` 日志，不适合库代码。

### 3.6 基准测试不严谨

现状：

1. `NUM_THREADS` 默认是 1。
2. 插入用 `rand()`，键空间和请求数相同，会产生很多重复 key。
3. 插入时打印成功日志，会严重污染 QPS。
4. 查询压测代码被注释掉了。
5. 没有 warmup、没有多轮统计、没有 P50/P99。

影响：

1. README 里的 QPS 结论参考价值有限。
2. 如果面试官细问，你必须主动说明这个 benchmark 不严谨。

### 3.7 存储格式脆弱

现状：

1. 文件格式是明文 `key:value`。
2. `value` 里如果包含换行或复杂分隔符，格式会出问题。
3. 没有 checksum，没有版本号，没有 schema。

影响：

1. 只能用于最简单场景。
2. 不具备工程上的可扩展性。

## 4. 面试里应该如何定位这个项目

建议的简历项目标题：

1. 基于 SkipList 的轻量级 KV 存储引擎改造项目

建议的项目描述方向：

1. 以跳表作为 MemTable 数据结构，实现 KV 的插入、删除、查询和有序遍历。
2. 在原始 Demo 基础上补齐并发控制、持久化恢复、测试与基准测试。
3. 通过结构化改造把算法练手项目升级为可讲工程权衡的存储项目。

你在面试里要主动强调：

1. 我知道它不是成熟数据库。
2. 我做这个项目的重点是把存储系统里的关键问题拆开并逐个补齐。
3. 我能解释清楚每个改造点背后的动机、权衡和收益。

## 5. 学习路线总览

建议按 6 个阶段推进，周期 4 到 8 周，视你的时间而定。

### 阶段 0：建立基线

目标：

1. 跑通项目。
2. 记录当前行为。
3. 建立你自己的理解坐标系。

任务：

1. 阅读 `README.md`、`main.cpp`、`skiplist.h`、`stress-test/stress_test.cpp`。
2. 亲手画出插入、查询、删除的路径图。
3. 记录当前接口、文件格式、线程模型和 benchmark 的局限性。
4. 自己复述一遍“项目目前到底实现了什么，没有实现什么”。

产出：

1. 一页自己的项目结构笔记。
2. 三张跳表操作路径图。
3. 一份当前问题清单。

验收标准：

1. 不看代码，你也能讲清 `insert_element` 的每一步。
2. 面试官问“为什么平均复杂度是 `O(log n)`”，你能回答。

### 阶段 1：吃透数据结构与源码

目标：

1. 把“会跑”升级成“会讲”。
2. 能把核心函数逐行解释清楚。

任务：

1. 重点理解 `update[]` 的作用。
2. 理解 `_skip_list_level` 的维护逻辑。
3. 解释 `get_random_level` 的概率模型。
4. 手推重复 key、删除头部、删除尾部、空表查询等边界场景。

产出：

1. 一份源码讲解文档。
2. 一组手工设计的边界测试用例。

验收标准：

1. 你能在白板上重新写出查找和插入的伪代码。
2. 你能指出当前实现中“泛型不彻底”和“线程安全不完整”的问题。

### 阶段 2：做 P0 级工程化改造

目标：

1. 让项目先变得“正确、干净、像库”。
2. 这是最重要的一阶段。

任务：

1. 加 include guard 或 `#pragma once`。
2. 去掉头文件里的全局变量，把锁和配置移到类成员。
3. 给项目加命名空间。
4. 把控制台日志改成可开关的日志或直接移除。
5. 修正 `load_file` 的泛型问题，引入比较器和序列化器抽象，或者至少明确只支持 `int` key。
6. 把递归析构改成迭代析构。
7. 补齐单元测试，覆盖插入、重复 key、删除不存在 key、落盘恢复、边界场景。

产出：

1. 一个面向库使用的更干净版本。
2. 第一版测试集。

验收标准：

1. 你能证明项目不再依赖头文件全局状态。
2. 你能用测试说明基本功能正确。

### 阶段 3：做 P1 级并发与 API 改造

目标：

1. 让项目开始具备“存储系统组件”的味道。
2. 解决面试里最容易被追问的并发问题。

任务：

1. 用 `std::shared_mutex` 或读写锁改造并发模型。
2. 明确哪些接口是读路径，哪些是写路径。
3. 重新设计返回值，避免仅靠打印日志表达结果。
4. 增加 `update` 语义，决定重复 key 是报错还是覆盖。
5. 增加 iterator 或 scan 接口，支持范围遍历。
6. 给 benchmark 增加多线程配置和无日志模式。

产出：

1. 更合理的 API。
2. 更可信的并发和性能结论。

验收标准：

1. 你能解释为什么读写锁适合这个场景。
2. 你能给出插入、查询、扫描的复杂度分析。

### 阶段 4：做 P1 级持久化改造

目标：

1. 从“全量 dump 文本”升级到“更像真实存储引擎”的恢复链路。

任务：

1. 设计 WAL，支持 `PUT`、`DELETE` 日志记录。
2. 写前日志先落盘，再更新内存跳表。
3. 启动恢复时先 replay WAL。
4. 增加 snapshot 或 checkpoint。
5. 设计崩溃恢复流程：加载 snapshot，再回放 WAL。
6. 给磁盘格式增加版本号和 checksum。

产出：

1. 一个可以讲清 crash recovery 的版本。
2. 一套恢复测试。

验收标准：

1. 你能回答“进程在写一半时崩溃怎么办”。
2. 你能画出启动恢复时序图。

验收标准：

## 7. 推荐的改造路线

### P0：先让项目“站得住”

这一阶段最重要，建议优先级最高。

改造项：

1. 增加 `#pragma once` 或 include guard。
2. 去掉 `skiplist.h` 中的全局 `mtx` 和 `delimiter`。
3. 为 `SkipList` 增加实例级锁。
4. 增加可配置的文件路径。
5. 规范返回值，避免业务逻辑依赖 `std::cout`。
6. 去掉递归析构。
7. 补测试。

价值：

1. 解决最基础的正确性和工程规范问题。
2. 这部分最容易被面试官认可。

### P1：补齐“像存储”的关键能力

改造项：

1. 引入 WAL。
2. 支持恢复。
3. 支持 scan。
4. 改造 benchmark。
5. 增加读写锁。

价值：

1. 面试时能自然聊到一致性、恢复、读写路径和性能权衡。

### P2：往真实引擎方向演进

改造项：

1. 引入 MemTable + Immutable MemTable。
2. 设计简化版 SSTable。
3. 做 compaction。
4. 做 Bloom Filter。
5. 增加配置系统和统计信息。

价值：

1. 这会让项目开始接近 LSM-tree 系统。
2. 但工作量更大，只有在你时间足够时才建议推进。

## 9. 你后续最值得真的去做的改进点

下面这些是我认为最值得投入的改进点。

### 改进点 1：把它从 Demo 改成真正可复用的库

方案：

1. 拆分 `skiplist.h`。
2. 增加命名空间、配置对象、状态码。
3. 去掉全局变量和硬编码文件路径。

收益：

1. 项目从“教程代码”升级成“组件代码”。

### 改进点 2：补齐并发正确性

方案：

1. 用实例级读写锁保护结构。
2. 所有读操作走共享锁。
3. 所有写操作走独占锁。
4. dump 时做一致性快照或锁保护。

收益：

1. 面试官追问线程安全时，你能给出明确答案。

### 改进点 3：补齐持久化与恢复

方案：

1. 增加 WAL。
2. 增加 checksum。
3. 增加 snapshot。
4. 恢复流程改成 `snapshot + WAL replay`。

收益：

1. 这是存储项目最核心的工程加分项之一。

### 改进点 4：重写 benchmark 和测试体系

方案：

1. 去掉业务日志输出。
2. 固定随机种子。
3. 支持多线程配置。
4. 区分随机写、顺序写、随机读、范围扫描。
5. 增加单测、压力测试、随机对拍测试。

收益：

1. 你的结果会更可信。
2. 面试时你能讲“我怎么证明我的实现是对的”。

### 改进点 5：向 LSM-tree 演进

方案：

1. 保留跳表作为 MemTable。
2. 增加 immutable memtable。
3. flush 成只读 SSTable。
4. 后续做 compaction 和 Bloom Filter。

收益：

1. 这条路线最能贴近 RocksDB/LevelDB 的核心思路。
2. 非常适合存储方向面试延展。

## 10. 简历上可以怎么写

在你完成至少一轮 P0 + P1 改造后，可以考虑这样写：

1. 基于 C++ 实现轻量级 KV 存储引擎，以 SkipList 作为内存索引结构，支持插入、删除、查询和有序遍历。
2. 设计并实现持久化恢复链路，引入 WAL 与 snapshot 机制，支持异常退出后的数据恢复。
3. 重构并发控制模型，使用读写锁区分读路径和写路径，补齐基础单元测试和性能基准测试。
4. 对压测链路进行无日志化和多线程改造，输出不同负载下的吞吐与延迟数据。

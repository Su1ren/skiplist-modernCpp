# Week 4 面试问答

## 1. 为什么跳表适合做 MemTable

跳表适合做内存态有序表，原因主要有三点。

第一，它天然维护 key 的全局有序关系，所以范围查询和顺序 dump 都很直接。像这个项目里的 `scan()`、snapshot 导出、WAL replay 后的有序状态恢复，都依赖这一点。

第二，它的插入、删除、查询平均复杂度都是 `O(logN)`，实现复杂度比红黑树低，工程上更容易讲清楚指针更新、层高随机化和空间换时间的权衡。

第三，跳表非常适合做“内存写缓冲层”。当前项目的写路径是 `WAL -> MemTable(skiplist)`，这个结构和很多 LSM 系统的前台写入模型是一致的。

## 2. 为什么需要 WAL + checkpoint

只有 snapshot 的话，两次 snapshot 之间的修改一旦进程异常退出就会丢失。

加入 WAL 之后，写路径先把操作追加到日志，再改内存。这样即使崩溃发生在内存更新前后，也至少有一份顺序日志可以在恢复时重放。

但如果只有 WAL，没有 checkpoint，恢复时间会随着日志变长而不断上升。所以还需要 checkpoint 定期把当前内存状态固化成 snapshot，然后把旧 WAL 清空。这样恢复时只需要：

1. 先加载 snapshot
2. 再回放 checkpoint 之后那一小段 WAL

这就是当前项目里 `snapshot + WAL` 的恢复链路。

## 3. 为什么当前只做到基础恢复，不继续做 SSTable / compaction

当前阶段的目标不是把项目做成完整数据库，而是先把“最小可讲清楚的存储恢复链路”做完整。

如果继续做 SSTable、后台 flush、compaction、Bloom Filter，就会把问题空间从“单机内存表 + 基础持久化”扩大到完整 LSM 存储层。那会引入更多新的工程主题：

* 文件格式设计
* 多层有序文件组织
* compaction 调度
* 读放大与写放大控制
* 校验和与损坏恢复

这些方向当然值得做，但它们已经超出当前这个仓库在 `Week 4` 的收口目标。现在的边界更适合作为面试里的第一阶段回答：

* 已经有 `WAL -> MemTable -> checkpoint -> recover`
* 具备基础可恢复能力
* 明确知道下一步应该如何演进到更完整的 LSM 结构

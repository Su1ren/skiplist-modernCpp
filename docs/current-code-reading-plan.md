# 当前代码阅读方案

## 目标

这份方案不是让你“快速扫一遍代码”，而是让你在最短时间内建立一套可复述、可画图、可面试表达的理解框架。读完之后，你应该能回答三类问题：

1. 当前项目实现了什么，没有实现什么。
2. 跳表的写路径、读路径、删除路径、持久化路径分别怎么走。
3. 这份代码为什么更像一个存储 Demo，而不是完整存储引擎。

## 建议的阅读顺序

建议按下面顺序读，不要一上来就从 `skiplist.h` 第一行看到最后一行。

### 第 0 步：先跑通项目，建立行为认知

先执行：

```bash
make
./bin/main
sh stress_test_start.sh
```

阅读目标：

1. 先从运行结果理解它对外提供的行为。
2. 记住当前 demo 展示了哪些接口。
3. 观察当前压力测试并不是真正严谨的 benchmark。

你此时只需要回答两个问题：

1. 这个项目对外暴露了哪些功能。
2. 这些功能里，哪些是“数据结构能力”，哪些是“存储能力”。

### 第 1 步：先读项目入口，不先读核心实现

先读：

1. `README.md`
2. `main.cpp`
3. `stress-test/stress_test.cpp`

阅读重点：

1. `main.cpp` 展示了当前主流程：插入、查询、删除、落盘、展示。
2. `stress_test.cpp` 说明作者想强调“性能”和“并发”，但当前实现默认线程数只有 1，而且日志输出很重。
3. 从入口文件反推你真正需要在 `skiplist.h` 里重点看哪几类函数。

本阶段你要输出：

1. 一张“项目文件职责图”。
2. 一张“主程序调用链图”。

### 第 2 步：只读类型定义和成员，不读函数体

接下来只看 `skiplist.h` 的声明部分，也就是：

1. `Node<K, V>`
2. `SkipList<K, V>`
3. 它们的成员变量和函数列表

阅读重点：

1. `Node` 为什么要有 `forward` 指针数组。
2. `node_level` 和 `forward[level + 1]` 的关系是什么。
3. `SkipList` 的 `_max_level`、`_skip_list_level`、`_header`、`_element_count` 各自负责什么。
4. 为什么这个实现把文件读写器也作为类成员。

这个阶段不要陷入实现细节，你只需要先建立“对象模型”。

本阶段你要输出：

1. 一张 `Node` 结构图。
2. 一张 `SkipList` 成员职责表。

### 第 3 步：重点攻克写路径

现在开始读写路径相关函数，顺序固定为：

1. `create_node`
2. `insert_element`
3. `get_random_level`

阅读重点：

1. `insert_element` 为什么要维护 `update[]`。
2. 为什么要从当前最高层往下走。
3. 为什么随机层高超过当前层高时，要把高层前驱补成 `_header`。
4. 当前重复 key 的行为是什么，为什么这会影响后续 API 设计。

你要做的动作：

1. 手动画一个 4 到 5 层的跳表示意图。
2. 亲手模拟一次插入新 key 的过程。
3. 再模拟一次插入重复 key 的过程。

本阶段你要输出：

1. 一张插入路径图。
2. 一段你自己的伪代码，不要照抄源码。

### 第 4 步：读查询和删除路径

接着读：

1. `search_element`
2. `delete_element`

阅读重点：

1. 查询为什么也是“先横向、再纵向”。
2. 删除为什么也要维护 `update[]`。
3. 删除后为什么还要回收 `_skip_list_level`。
4. 当前查询没有加锁，这意味着什么。

你要做的动作：

1. 画出一次成功查询路径。
2. 画出一次失败查询路径。
3. 画出删除中间节点和删除最高层节点的差异。

本阶段你要输出：

1. 一张查询路径图。
2. 一张删除路径图。
3. 一份删除边界场景清单。

### 第 5 步：读持久化路径

接着读：

1. `dump_file`
2. `load_file`
3. `get_key_value_from_string`
4. `is_valid_string`

阅读重点：

1. 当前项目的持久化不是 WAL，而是全量文本 dump。
2. 文件格式为什么脆弱。
3. `load_file` 里为什么说模板是“半泛型”。
4. 为什么 `value` 一旦变复杂，当前 `key:value` 格式就会出问题。

你要做的动作：

1. 打开 `store/dumpFile`，确认真实落盘格式。
2. 思考如果 `value` 里包含 `:` 或换行会发生什么。
3. 思考为什么这条恢复链路不具备真正的崩溃一致性。

本阶段你要输出：

1. 一张“内存 -> dump 文件 -> load 重建”的流程图。
2. 一份持久化缺陷清单。

### 第 6 步：读构造、析构和资源管理

接着读：

1. `SkipList` 构造函数
2. `~SkipList`
3. `clear`

阅读重点：

1. 头节点为什么这样初始化。
2. 析构为什么依赖递归删除。
3. 当数据量大时，递归释放为什么有栈深风险。
4. 文件句柄关闭逻辑有没有明显问题。

本阶段你要输出：

1. 一份资源生命周期笔记。
2. 一份内存管理风险清单。

### 第 7 步：最后读并发与压测，不要提前读

最后再回到：

1. `std::mutex mtx`
2. `insert_element` / `delete_element` 中的加锁
3. `search_element`、`dump_file`、`load_file` 的无锁路径
4. `stress-test/stress_test.cpp`

阅读重点：

1. 当前锁为什么是头文件全局锁。
2. 为什么这个设计会让所有 `SkipList` 实例共享一把锁。
3. 为什么只给写路径加锁，不等于线程安全。
4. 为什么当前压测不能证明真实并发性能。

你要做的动作：

1. 用一句话定义当前项目的并发模型。
2. 列出至少 5 个“面试官会追问”的并发问题。
3. 把这些问题和后续 P0/P1 改造方案对应起来。

本阶段你要输出：

1. 一份并发问题清单。
2. 一份 benchmark 局限性清单。

## 推荐的阅读节奏

如果你只有 2 天：

1. 第 1 天完成第 0 到第 4 步。
2. 第 2 天完成第 5 到第 7 步，并整理风险清单。

如果你有 3 到 4 天：

1. 第 1 天跑通项目并读入口。
2. 第 2 天只读数据结构和写路径。
3. 第 3 天读查询、删除、持久化。
4. 第 4 天读资源管理、并发和 benchmark，并整理自己的项目讲稿。

## 阅读时必须带着的问题

每读一段代码，都强制回答下面的问题：

1. 这个函数的输入、输出、状态修改分别是什么。
2. 这个函数依赖哪些类成员。
3. 这个函数有没有并发风险。
4. 这个函数有没有边界条件没有处理好。
5. 如果让我改造它，我会先改接口、实现、还是测试。

## 你读完后应当能直接说出的结论

1. 当前项目是“跳表 + 全量文本 dump”的轻量 KV Demo。
2. 它实现了基本增删查和简单恢复，但没有 WAL、checkpoint、SSTable、compaction。
3. 当前实现最大的工程问题是全局锁、半泛型持久化、递归析构和不严谨的 benchmark。
4. 它适合做存储面试项目的起点，但需要经过 P0/P1 改造，才能变成质量更高的简历项目。

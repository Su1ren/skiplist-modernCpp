# Skiplist-CPP 内存管理风险清单

## 1. 文档范围

这份清单只审视 `skiplist.h` 当前实现中的内存管理与内存安全风险，不展开持久化一致性问题。

判断标准主要有三类：

1. 是否可能泄漏内存
2. 是否可能发生非法释放、重复释放或悬空访问
3. 是否存在明显脆弱的手工生命周期管理点

## 2. 结论概览

当前实现的主要风险不是“每次操作都会稳定泄漏”，而是：

1. 资源所有权全靠人工维护，异常安全较弱
2. 并发读写下存在悬空指针访问风险
3. 析构路径依赖递归，数据量大时清理链路不稳

## 3. 风险清单

### 3.1 P0：并发读和删除并存时，存在悬空指针访问风险

代码位置：

1. `display_list` `skiplist.h:282-296`
2. `dump_file` `skiplist.h:298-321`
3. `search_element` `skiplist.h:476-508`
4. `delete_element` `skiplist.h:395-455`

问题描述：

1. 读路径没有加锁。
2. 删除路径会在摘链后直接 `delete current`。
3. 如果读线程正持有某个节点指针，写线程可能在另一侧把这个节点释放掉。

后果：

1. 读线程继续解引用该节点时，会触发 use-after-free。
2. 这类问题通常表现为随机崩溃、错误输出或极难复现的未定义行为。

为什么这是内存安全问题：

1. 这里不是普通“线程安全不完整”，而是“对象可能已经释放，但还有线程继续访问它”。

### 3.2 P0：`clear` 递归释放节点，数据量大时可能栈溢出，导致清理不完整

代码位置：

1. `skiplist.h:555-566`
2. `skiplist.h:528-553`

问题描述：

1. `~SkipList()` 通过递归 `clear` 销毁整条第 0 层链。
2. 如果节点数量很大，递归深度会与元素个数近似线性相关。

后果：

1. 在大数据量下，析构阶段可能栈溢出。
2. 一旦崩溃，剩余节点无法继续释放，形成进程退出前的清理失败。

判断：

1. 这更像“释放路径不稳”而不是常规小规模泄漏。
2. 但在长期运行或大规模场景中，它会直接影响内存回收可靠性。

### 3.3 P0：`Node` 默认构造函数不初始化 `forward`，析构时可能非法释放

代码位置：

1. `skiplist.h:35`
2. `skiplist.h:76-82`

问题描述：

1. `Node()` 是公开的空实现。
2. 这个构造函数不会初始化 `forward`。
3. `~Node()` 却无条件执行 `delete[] forward`。

触发条件：

1. 只要后续有人默认构造一个 `Node`，然后离开作用域或手工 `delete`，就可能对未初始化指针执行 `delete[]`。

后果：

1. 非法释放
2. 崩溃
3. 未定义行为

说明：

1. 当前主路径没有使用默认构造函数，但接口本身已经暴露了风险入口。

### 3.4 P1：`load_file` 中手工 `new` 的字符串在异常路径上可能泄漏

代码位置：

1. `skiplist.h:335-350`
2. `skiplist.h:346`

问题描述：

1. `key` 和 `value` 通过 `new std::string()` 申请。
2. 它们只在函数尾部 `delete`。
3. 如果 `stoi(*key)` 抛异常，或者后续插入路径未来引入异常，这两个堆对象不会被释放。

后果：

1. 方法异常退出时会产生小规模堆泄漏。
2. `_file_reader.close()` 也会被跳过，文件句柄只能等对象析构时再释放。

更合理的做法：

1. 这里应直接使用栈对象 `std::string key; std::string value;`。

### 3.5 P1：`Node` 持有裸指针但没有显式禁止拷贝，存在双重释放风险

代码位置：

1. `skiplist.h:30-57`
2. `skiplist.h:76-82`

问题描述：

1. `Node` 自己管理 `forward` 的堆内存。
2. 类里没有自定义拷贝构造、拷贝赋值，也没有显式 `delete` 掉这些操作。
3. 如果节点对象按值拷贝，两个对象会共享同一块 `forward` 指针。

后果：

1. 两个副本析构时都会执行 `delete[] forward`。
2. 最终触发 double free。

说明：

1. 当前代码路径主要通过 `Node*` 使用节点，没有直接按值复制。
2. 但类定义本身没有把这种危险用法从类型系统层面禁止掉。

### 3.6 P1：插入和删除使用按运行时大小决定的栈数组，大配置下存在栈内存压力

代码位置：

1. `skiplist.h:203-205`
2. `skiplist.h:406-407`

问题描述：

1. `update[_max_level + 1]` 依赖运行时的 `_max_level`。
2. 这在标准 C++ 里不是标准数组写法，通常依赖编译器扩展。
3. 如果 `_max_level` 很大，每次操作都会在栈上放一大块指针数组。

后果：

1. 可能带来栈空间压力。
2. 也会降低代码的可移植性和生命周期可预测性。

说明：

1. 这不是堆泄漏问题。
2. 但它属于典型的“内存布局和资源承载方式不稳”。

### 3.7 P1：析构阶段没有并发隔离，可能在对象销毁时删除仍被其他线程使用的节点

代码位置：

1. `skiplist.h:528-566`
2. `skiplist.h:186-280`
3. `skiplist.h:395-455`
4. `skiplist.h:476-508`

问题描述：

1. `~SkipList()` 不会阻止其他线程继续读写。
2. 如果外部在对象析构期间仍有并发访问，析构会递归释放节点。

后果：

1. 其他线程可能访问已经被 `clear` 删除的节点。
2. 这是对象级别的 use-after-free 风险。

说明：

1. 严格说这依赖调用方是否保证析构前停机。
2. 但当前类本身没有防御机制。

## 4. 当前代码里哪些点暂时没有明显泄漏

下面这些地方虽然实现风格偏手工，但在正常无异常路径上没有明显持续泄漏：

1. `create_node` 分配出来的节点，在删除路径和析构路径上都有对应 `delete`
2. `Node` 的 `forward` 数组，在节点析构时有对应 `delete[]`
3. `dump_file` 和 `load_file` 的文件流，在正常路径上都会 `close`

这也是为什么当前问题更偏“脆弱”和“异常/并发下不安全”，而不是“主流程稳定泄漏”。

## 5. 优先修复建议

建议优先级如下：

1. 先修读写并发导致的 use-after-free，把读路径和析构路径的并发约束补齐。
2. 再把递归 `clear` 改成迭代释放，避免大规模数据下的栈溢出。
3. 删掉 `Node()` 默认构造函数，或者至少把 `forward` 初始化为 `nullptr`。
4. 把 `load_file` 的 `key`、`value` 改为栈对象。
5. 显式删除 `Node` 的拷贝构造和拷贝赋值，避免误用。
6. 把 `update` 改为 `std::vector<Node<K, V>*>`，消除非常规栈数组。

## 6. 一句话结论

当前实现最大的内存管理问题，不是简单的“忘记 delete”，而是裸指针所有权、并发释放和递归清理三者叠加后，整体内存安全边界比较脆弱。

# Skiplist-CPP benchmark 局限性清单

## 1. 一句话结论

当前 `stress-test/stress_test.cpp` 更接近“粗略压测脚本”，不能作为严谨性能结论的依据。

## 2. 当前 benchmark 在测什么

代码入口：

1. [stress-test/stress_test.cpp](../stress-test/stress_test.cpp)

当前主路径实际测的是：

1. 创建若干线程
2. 让每个线程循环调用 `insert_element`
3. 统计从建线程到全部 `join` 的总耗时

它没有真正建立：

1. 明确 workload 定义
2. 稳定数据分布
3. 可重复结果
4. 多轮统计模型

## 3. 局限性清单

### 3.1 只测插入，查询测试被注释掉

现状：

1. `getElement` 存在
2. 但查询压测主流程被整段注释

影响：

1. 只能得到“插入大概多快”
2. 无法评价查询、删除、混合负载和读写竞争

### 3.2 多线程存在，但写路径被全局锁串行化

现状：

1. benchmark 创建多个线程
2. `insert_element` 内部使用全局 `mtx`

影响：

1. 即使线程数增加，核心写路径仍然是串行临界区
2. 这个 benchmark 不能直接证明良好的并发扩展性

### 3.3 benchmark 被大量日志严重污染

现状：

1. 线程创建时打印日志
2. 每个线程启动会打印线程 id
3. `insert_element` 每次成功插入都会打印

影响：

1. I/O 时间会大量掺进统计结果
2. 得到的更像“带大量标准输出的程序吞吐”，不是内存结构真实性能

### 3.4 key 分布会产生大量重复插入

现状：

1. 插入 key 使用 `rand() % TEST_COUNT`
2. 总操作数也是 `TEST_COUNT`

影响：

1. 大量操作会命中重复 key
2. 真实成功插入条数小于请求数
3. benchmark 没有区分“请求吞吐”和“成功写入吞吐”

### 3.5 随机种子不固定，结果不具备良好可复现性

现状：

1. `srand(time(nullptr))`

影响：

1. 每次运行 key 分布不同
2. 多次结果横向比较不稳定

### 3.6 只统计单次总耗时，没有 warmup 和多轮统计

现状：

1. 代码只测一轮
2. 没有预热阶段
3. 没有中位数、方差、P95/P99

影响：

1. 结果非常依赖单次运行状态
2. 难以判断波动和稳定性

### 3.7 把建线程和回收线程开销直接算进业务耗时

现状：

1. 计时从 `pthread_create` 前开始
2. 到全部 `pthread_join` 后结束

影响：

1. 测出来的不只是数据结构操作耗时
2. 线程创建和回收成本会干扰核心操作的比较

### 3.8 没有做结果校验

现状：

1. benchmark 跑完只输出耗时
2. 没有验证最终数据规模和正确性

影响：

1. 无法确认 benchmark 是否在正确条件下完成
2. 性能数字和正确性被完全解耦

### 3.9 没有设置不同 workload、不同 key-space、不同线程数矩阵

现状：

1. 线程数、请求数都是编译期常量
2. 没有命令行参数
3. 没有不同场景的系统化对比

影响：

1. 很难回答“线程数上去后怎么样”
2. 很难回答“key 分布变化后怎么样”

### 3.10 没有外部 baseline 对照

现状：

1. 没有和 `std::map`、`std::unordered_map` 或其他结构对比

影响：

1. 单独一个 QPS 数字的解释力很弱
2. 很难判断当前实现到底快在哪里，慢在哪里

### 3.11 README 中的 QPS 数据缺少完整实验说明

现状：

1. README 给出了 QPS 数字
2. 但没有完整说明线程数、日志开关、随机种子、机器配置、是否命中重复 key

影响：

1. 数字可参考，但不够可审计
2. 面试里如果被追问实验方法，需要主动承认局限

## 4. 面试里推荐的说法

你可以直接这样讲：

1. 当前 benchmark 只能证明“项目能在一定规模下跑起来”，不能证明它有可信的并发性能结论。
2. 最大的问题是日志污染、重复 key 干扰、缺少查询和混合负载、没有多轮统计。
3. 如果继续改造，我会先把 benchmark 参数化，再补正确性校验、无日志模式、固定随机种子和多 workload 矩阵。

## 5. 最值得优先修的三件事

1. 去掉核心路径日志，先建立无噪音基线。
2. 把 workload 参数化，至少支持线程数、操作数和 key-space。
3. 补上查询和混合负载，并对结果做正确性校验。

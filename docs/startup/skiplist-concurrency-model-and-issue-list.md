# Skiplist-CPP 当前并发模型和问题清单

## 1. 一句话定义

当前项目的并发模型可以概括为：

1. 全局单锁串行化写路径
2. 多数读路径无锁
3. 持久化和析构路径也没有完整并发隔离

换句话说，它不是“线程安全跳表”，而是“只给部分写操作加了一把全局锁”。

## 2. 当前并发模型

### 2.1 锁的形态

当前锁定义在 `skiplist.h` 头文件里：

1. `std::mutex mtx`

这意味着：

1. 它不是 `SkipList` 成员锁
2. 它是进程级全局可变状态
3. 所有 `SkipList` 实例共享同一把锁

### 2.2 哪些路径会加锁

当前加锁路径：

1. `insert_element`
2. `delete_element`

当前无锁路径：

1. `search_element`
2. `display_list`
3. `dump_file`
4. `load_file`
5. `size`
6. `~SkipList`

### 2.3 并发语义的真实效果

1. 多个线程同时插入时，真正修改结构的临界区会被这把全局锁串行化。
2. 多个不同 `SkipList` 实例之间也会互相抢同一把锁。
3. 查询和遍历看起来可以并发执行，但因为无锁，它们并不安全。
4. 压测里虽然创建了多个线程，但并不等于实现了合理的多线程读写模型。

## 3. 当前问题清单

### 3.1 P0：全局锁放在头文件里，实例之间错误共享

问题：

1. 所有实例竞争同一把锁。
2. 这不是对象级并发控制，而是进程级粗粒度串行化。

影响：

1. 多实例场景下不合理。
2. 还会带来多翻译单元的 ODR 风险。

### 3.2 P0：读路径无锁，和写路径并发时有数据竞争

问题：

1. `search_element`、`display_list`、`dump_file` 都会遍历节点指针。
2. `delete_element` 会在改链后直接释放节点。

影响：

1. 读线程可能访问已经删除的节点。
2. 这不是简单的“读到旧值”，而是潜在的 use-after-free。

### 3.3 P0：`dump_file` 无锁遍历，拿不到一致快照

问题：

1. `dump_file` 遍历 level 0 时，如果有线程同时插入或删除，文件内容可能混杂前后两个时刻的数据。

影响：

1. 落盘文件不一定代表某一个真实时刻的完整状态。
2. 后续 `load_file` 的恢复基础本身就可能不可靠。

### 3.4 P0：析构阶段没有并发停机机制

问题：

1. `~SkipList` 会递归删除整条链，但没有阻止其他线程继续访问。

影响：

1. 如果对象销毁时外部线程仍在读写，会直接触发对象级悬空访问。

### 3.5 P1：`load_file` 的并发语义不清晰

问题：

1. `load_file` 自己无锁，但内部会调用带锁的 `insert_element`。
2. 这意味着“加载一份文件”不是原子操作，而是一系列分散的插入。

影响：

1. 其他线程可能读到一个“加载到一半”的中间状态。
2. 也可能和运行中的写路径交织，产生难解释的结果。

### 3.6 P1：`size` 无锁，统计值在并发场景下不可靠

问题：

1. `_element_count` 会在写路径修改。
2. `size()` 直接返回，没有同步保护。

影响：

1. 并发读到的值可能过期。
2. 从 C++ 内存模型角度看，这也是共享可变状态的无同步访问。

### 3.7 P1：当前锁模型不支持读多写少优化

问题：

1. 当前只有一把普通互斥锁。
2. 即使以后把读路径也加锁，也只能做到“全局互斥”，不能做到“并发读，互斥写”。

影响：

1. 与典型存储场景的读多写少负载不匹配。
2. 后续要演进到更合理的模型，通常需要实例级读写锁。

## 4. 压测和并发模型的关系

当前 `stress_test.cpp` 里的多线程压测不能证明线程模型合理，原因有三点：

1. 写路径被全局锁串行化，扩容到多线程后不会自然体现真实可扩展性。
2. 压测包含大量 `std::cout`，I/O 干扰远大于锁竞争分析价值。
3. 查询压测代码被注释掉，读写混合场景没有被验证。

## 5. 面试里推荐的表达方式

你可以直接这样讲：

1. 当前实现不是严格线程安全。
2. 它只给插入和删除加了一把头文件全局锁，本质上是粗粒度串行写。
3. 查询、遍历、落盘和析构都缺少完整并发保护，因此存在数据竞争和悬空访问风险。
4. 如果继续改造，我会把它升级成实例级读写锁模型，并重新定义恢复和遍历接口的并发语义。
